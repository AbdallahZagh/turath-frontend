Technical Architecture & Strategic Feasibility Report: Turath Platform (تراث)
Track 1: Regional Technical Feasibility & Infrastructure Optimization
1.1 Connectivity & Mapping Services
Deploying an interactive GIS and mapping infrastructure within the Syrian hospitality sector requires overcoming substantial structural headwinds, including international compliance constraints under OFAC regulations, foreign payment gateway blacklists, intermittent mobile network connectivity, and severely outdated commercial base layers in historical urban centers1. Commercial proprietary mapping providers present operational and technical liabilities in this operational environment:
Google Maps Platform: Enforces strict API credit card billing mechanisms that reject regional financial instruments, periodically blocks client IP blocks originating from Syrian autonomous systems due to blanket compliance policies, and provides inconsistent Arabic typography across historical alleyways such as Old Damascus, Bab Touma, and the Ancient City of Aleppo1.
Mapbox GL: Imposes comparable export-control constraints and metered usage costs denominated in foreign fiat currencies, while its client-side SDKs generate substantial network telemetry that fails under high packet-loss conditions1.
Leaflet with Public Raster OSM: Eliminates licensing dependencies but introduces severe performance bottlenecks; raster tiles consume significant client bandwidth, lack dynamic client-side vector styling, and exhibit noticeable visual stutter during multi-touch zooming over high-latency cellular networks1.
The optimal architectural pattern consists of a decoupled, self-hosted vector tile infrastructure utilizing OpenStreetMap (OSM) source data, compiled into single-file PMTiles archives via Planetiler, and rendered natively via MapLibre GL across both web and mobile clients3.

Cartographic Pipeline Architecture
The cartographic engineering pipeline operates through four discrete stages:
Source Data Ingestion: Automated weekly extraction scripts pull the latest Syria country extract (syria-latest.osm.pbf) from Geofabrik.
Vector Tile Generation: A containerized Planetiler build pipeline transforms the .osm.pbf extract into an optimized single-file syria.pmtiles archive. The build configuration explicitly maps Arabic name priority (name:ar  name  int_name), ensuring that all historical quarters, souks, and cultural landmarks render correct Arabic typography.
Distribution & Edge Proxying: The generated syria.pmtiles file is hosted on S3-compatible cloud object storage (e.g., MinIO) behind an Nginx caching reverse proxy configured with HTTP/2 range-request support4.
Self-Hosted Geocoding Engine: Address resolution and reverse geocoding execute via an isolated Nominatim or Pelias instance seeded exclusively with Syrian administrative boundaries, eliminating all outbound external third-party API dependencies.
1.2 Multi-Channel OTP & Telephony Reliability
Mobile communications in Syria are split between two primary mobile network operators: Syriatel (Mobile Country Code 417, Mobile Network Code 01), commanding approximately 55.6% market share with 7.1 million subscribers, and MTN Syria (MCC 417, MNC 02), holding roughly 44.4% market share with 5.7 million subscribers6. Direct international Application-to-Person (A2P) SMS termination via global telecommunications aggregators (such as Twilio or Sinch) experiences failure rates exceeding 40% due to international routing blocks, grey routes, and elevated costs ranging between €0.21 and €0.38 per message6.
To ensure an authentication completion rate above 99.5% during intermittent network degradation, the platform must implement an automated, multi-tiered fallback orchestration engine.
Multi-Tier Authentication Fallback Flow
Tier 1: Data-Driven Messaging (0–25 Seconds): When a user requests an OTP on Web or Mobile, the backend dispatches an encrypted verification template via the WhatsApp Business Cloud API or regional WhatsApp enterprise aggregators1. This channel bypasses cellular SMS congestion, operates over local Wi-Fi during telecommunications outages, and reduces delivery costs to approximately €0.01 per conversation7.
Tier 2: Direct Local SMS Gateway (25–60 Seconds): If delivery confirmation is not received within 25 seconds, the system falls back to programmatic HTTP REST integration with certified local aggregators (such as EconSMS or direct carrier SMPP binds)10. The engine identifies the carrier prefix—routing +963 93, +963 98, and +963 99 to Syriatel, and +963 94, +963 95, and +963 96 to MTN Syria—to minimize inter-carrier routing latencies12.
Tier 3: Voice Flash-Call / Fallback SMS (60–90 Seconds): If the OTP remains unacknowledged after 60 seconds, an automated Interactive Voice Response (IVR) flash-call or secondary aggregator SMS route is triggered9.
Resiliency & Abuse Mitigation Controls
Carrier Health Circuit Breaker: A Redis-backed sliding-window counter monitors delivery receipt (DLR) latency over the preceding 100 outbound requests per carrier. If average delivery latency exceeds 30 seconds or the failure threshold crosses 15%, the system trips a circuit breaker and promotes WhatsApp as the mandatory primary route platform-wide7.
Rate Limiting & Cost Shields: Outbound requests are throttled using a leaky bucket algorithm enforcing a maximum of 3 OTP requests per phone number per 15-minute window, and 5 requests per IP address per minute.
Cryptographic Attestation: Mobile requests must supply a short-lived client attestation token generated via Google Play Integrity API or Apple DeviceCheck to prevent scripted SMS credit exhaustion attacks.
1.3 Offline Sync & Storage Strategy
In historical destinations (such as the Old City of Damascus or Krak des Chevaliers), cellular reception often drops entirely1. The Flutter mobile architecture must therefore operate as an offline-first execution environment1.
The client persistence layer is organized hierarchically:
Relational Pass Data & Audit Queues: Handled via Drift (a type-safe SQLite abstraction), compiled with SQLCipher for full on-disk AES-256 encryption1.
Ephemeral Presentation State & Geodata: Managed via Hive, providing low-latency key-value keyrings for temporary UI filters and tile index pointers1.
Cryptographic Key Management: Master encryption keys are generated on-device and secured inside flutter_secure_storage, backed by iOS Keychain and Android KeyStore (enforcing hardware-backed StrongBox where supported).

Reconnection Synchronization Routine
The client synchronization engine implements a deterministic state machine:
Network Connectivity Detection: Monitored via the connectivity_plus plugin, augmented with active lightweight HTTP HEAD health checks to Turath edge nodes to confirm WAN transit.
Outbound Audit Queue Drainage: The app drains records from offline_scan_audit_queue to the backend /api/v1/qr/sync-scans endpoint using an idempotent batching protocol. Each scan record includes a client-generated UUID (scan_id) to prevent duplicate ledger postings during partial network failures.
Inbound Delta Synchronization: The client presents its high-watermark timestamp (last_sync_timestamp). The server calculates a binary delta payload containing updated reservation statuses, provider schedule revisions, and revoked voucher hashes, updating the local SQLite tables within a single atomic database transaction.
Track 2: Concurrency, Inventory Locking & Anti-Double-Booking Architecture
2.1 Distributed Mutex & Transaction Isolation
High-demand booking scenarios—such as flash ticket releases for major cultural events, boutique hotel reservations during peak holiday seasons, or prime weekend dining table allocations—require robust concurrency isolation1. Relying solely on relational database row-level locking can lead to database thread pool exhaustion and unacceptable latency spikes under sudden load surges.
Turath employs a two-tiered concurrency control pipeline:
Tier 1 (Volatile Distributed Hold): A high-throughput Redis distributed mutex that atomically evaluates inventory availability and creates a temporary hold with a strict 10-minute Time-To-Live (TTL).
Tier 2 (Durable Relational Commitment): A transactional PostgreSQL persistence routine utilizing pessimistic row-level locking (SELECT ... FOR UPDATE) executing within a READ COMMITTED isolation boundary to record the final booking and update the financial ledger1.

To prevent race conditions between checking available capacity and decrementing the inventory counter, the volatile hold is acquired atomically using a Lua script executed directly on the Redis primary node:

Lock Cleanup Workers & Asynchronous Rollback
To ensure that abandoned reservations do not leave inventory locked indefinitely:
Redis Expiration Events: Keys in the hold registry are assigned a 10-minute TTL.
Asynchronous BullMQ Sweeper: A BullMQ background worker listens for expired lock keys and executes a compensating Redis transaction to restore the available inventory counter.
Database Rebalancing Cron: A scheduled cron job runs every 5 minutes to identify any bookings in PENDING_CONFIRMATION status that have exceeded their time limit, automatically transitioning them to EXPIRED and releasing their held resources.
2.3 Cryptographic QR Validation & Asymmetric Hardening
Vulnerability Analysis of Initial Symmetric Specification
The initial specification proposes an HMAC-based symmetric signing mechanism:
[cite: 1]
This architecture introduces three critical vulnerabilities:
Symmetric Secret Compromise: Verifying an HMAC signature offline requires distributing the shared secret key to thousands of provider mobile devices1. Extracting this key via static reverse engineering (e.g., using Frida or Ghidra on the Flutter binary) allows malicious actors to forge arbitrary valid check-in passes.
Replay Attacks on Offline Scanners: In the absence of real-time database lookups, a valid QR pass can be presented to multiple staff scanners simultaneously or rescanned across different gates before sync occurs1.
Clock Drift & Device Time Tampering: Devices operating offline may drift or have their system clocks manually rolled back to accept expired vouchers.
Hardened Asymmetric Ed25519 Protocol
The cryptographic engine must transition to asymmetric digital signatures using Edwards-curve Digital Signature Algorithm (Ed25519)13. The private key remains in an isolated Hardware Security Module (HSM) / backend Key Management Service, while provider applications embed only the public key13.

Camera Stream Capture: The staff scanner captures the QR payload using the high-speed camera engine1.

Track 3: Business Model, Leakage Prevention & Trust Engine (Cash on Arrival)
3.1 Commission Collection & Leakage Control
In a Cash on Arrival (COA) operational model, the platform faces financial leakage risks: service providers may falsely report arriving tourists as no-shows, or collude with guests to cancel on-platform bookings for an unrecorded cash discount1. Because digital escrow is infeasible in the MVP phase due to banking constraints, the platform enforces compliance using game-theoretic incentive structures, automated auditing, and behavioral tripwires1.
Automated Tourist Handshake Verification
Whenever a provider flags a reservation as NO_SHOW or requests a manual cancellation at the venue, the system automatically dispatches an interactive inquiry to the tourist via WhatsApp and Push Notification: "Our records indicate you did not complete your reservation at [Provider Name]. Please confirm if you attended."
[cite: 1, 7]
If the tourist indicates successful attendance, the system triggers the following automated actions:
The booking status immediately transitions to DISPUTED_COMPLETION.
The standard commission fee is accrued to the provider's ledger balance1.
A punitive dispute assessment fee (e.g., 200% of standard commission) is levied against the provider.
The provider's listing visibility is deprioritized in search results.
Review Eligibility Gating & Loyalty Incentives
Only reservations verified through a cryptographic QR code scan unlock the ability to submit verified ratings and reviews1. To incentivize tourists to insist on formal check-in scans, completed digital check-ins award Platform Loyalty Credits (redeemable for future platform-subsidized promotions) and increase the user's platform trust standing1.
Spotlight Promotions vs Cash-on-Arrival Coupons
Homepage merchandising (featured listings and home campaigns on /admin/promotions) is advertising only: it pins a listing or a themed band on the tourist home for a date window. It does not change the cash amount due. This existing Promotions page remains separate from discount codes.
Cash-on-arrival coupons are a separate Super Admin catalog (/admin/coupons). After the admin agrees a deal with a provider (or funds a platform- / pillar-wide subsidy), they publish a code with a percent or fixed SYP discount, a scope, dates, and optional caps. The tourist enters the code at booking; the voucher and provider desk show the discounted cash due. Ledger commission uses that collected total. Coupons never charge a card. Platform Loyalty Credits remain a later, platform-subsidized incentive and are not this coupon catalog. Providers do not self-serve coupons in the MVP.
Dynamic Margin Tiering
The platform applies a dynamic commission model that rewards transparent reporting:
Standard Commission Rate: 12% across completed reservations1.
Preferred Tier (Low Dispute Rate): Providers maintaining a dispute rate below 2% and a no-show rate matching regional baseline distributions see their commission rate reduced to 8.5%.
High-Risk Penalty Tier: Providers whose cancellation and no-show ratios deviate by more than 2.5 standard deviations from the governorate average are subject to an elevated 18% commission rate and targeted for mystery shopper audits.

Track 4: UI/UX & Frontend Architecture (Next.js 15+ & Flutter)
4.1 Next.js Web Architecture
The web architecture is structured around Next.js 15+ using the App Router, separating public discovery, provider operations, and super-administrative control into isolated route groups1. Server and Client Component boundaries are strictly enforced to achieve sub-second Core Web Vitals (LCP < 1.2s, CLS = 0, INP < 100ms) even over degraded 3G networks1.
The file structure enforces separation across three route groups:
src/app/(public)/: Public discovery pages, attraction directories, and booking funnels. These leverage React Server Components (RSC) and Incremental Static Regeneration (ISR) to maximize SEO performance and minimize client JavaScript payloads1.
src/app/(provider)/: Provider business management dashboards, live table layout editors, and inventory planners, guarded by organization-level RBAC middleware1.
src/app/(admin)/: Super Admin management interface for KYC pipeline reviews, financial reconciliation, CMS curation, homepage promotions merchandising, and the cash-on-arrival coupon catalog1.
State Management & Performance Boundaries
Server State: Managed via TanStack Query v5 (@tanstack/react-query), providing background revalidation, server-side prefetching hydration, and optimistic UI mutations for reservation workflows.
Client Ephemeral State: Managed via Zustand stores with persistent local storage middleware for UI states (e.g., dynamic filter drawers, active map bounding boxes, currency display preferences).
RSC Optimization Pattern: All listing descriptions, historical landmark narratives, and provider metadata are rendered as static React Server Components. Interactive elements (e.g., date-range pickers, dynamic seat maps, review forms) are extracted into isolated client islands ('use client').
4.2 Flutter Cross-Platform Architecture
The mobile application is designed according to Clean Architecture principles, enforcing separation of concerns between Data, Domain, and Presentation layers. It operates in two runtime modes: Tourist Mode and Provider Mode1.
The codebase is organized into modular feature layers:
lib/core/: Cryptographic utilities (Ed25519 verifiers), local database engines (Drift SQLCipher), network client configurations (Dio with exponential backoff retry interceptors), and localization themes13.
lib/features/discovery/: Map interfaces, search filters, and point-of-interest details powered by Riverpod state providers1.
lib/features/wallet/: Local encrypted pass storage and high-contrast offline QR rendering1.
lib/features/scanner/: Hardware-accelerated camera barcode scanning pipeline for provider staff1.

4.3 Bilingual RTL/LTR Design System & Localization
The user interface provides native bidirectional support for Arabic (Right-to-Left) and English (Left-to-Right), incorporating dynamic dual-currency calculations.
Arabic Typography & Layout Rules
Typography Pipeline: Cairo and IBM Plex Sans Arabic serve as the primary typefaces. Arabic typography requires a +25% vertical line-height multiplier compared to standard Latin typography to prevent clipping of complex diacritics and ligatures across mobile viewports.
Layout Mirroring via Logical Properties: Layout dimensions are defined using CSS logical properties (margin-inline-start, padding-inline-end, inset-inline-start) in Next.js and EdgeInsetsDirectional in Flutter.
Directional Iconography: Navigation chevrons, arrows, back buttons, and step indicators mirror automatically when switching between RTL and LTR, while functional brand icons (e.g., camera, map pin, telephone) remain unmirrored.
Dual-Currency Conversion Engine: All database records store amounts in Syrian Pounds (SYP)1. The UI dynamically renders equivalent USD valuations pegged to an administrative platform exchange rate: "150,000 SYP (~$10.50 USD)"1.

Architectural Synthesis
The architectural blueprint for the Turath platform addresses the technical and socio-economic constraints of the Syrian hospitality landscape1:
Infrastructure Independence: Replacing external cloud-dependent mapping services with self-hosted PMTiles and MapLibre GL eliminates sanctions risks, avoids foreign billing liabilities, and delivers offline vector map rendering3.
Deterministic Resiliency: The multi-tiered authentication engine mitigates local telecom failure modes by prioritizing cost-effective WhatsApp channels before routing through local carrier gateways7.
Mathematical Concurrency Integrity: Combining Redis distributed mutexes with PostgreSQL pessimistic locking ensures that multi-tenant inventories across hotels, dining tables, trips, and events remain consistent under traffic spikes without double-booking1.
Zero-Trust Offline Verification: Shifting from symmetric HMAC tokens to asymmetric Ed25519 signatures allows provider staff to authenticate bookings instantly in network-degraded historical quarters while guarding against replay attacks and credential extraction1.
Economic Alignment: The game-theoretic trust and reliability engine aligns economic incentives in a Cash-on-Arrival model, minimizing platform leakage and ghost bookings through automated verification handshakes and dynamic margin structures1.
